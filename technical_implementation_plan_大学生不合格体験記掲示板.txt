技術的実装段階計画書：大学生向けの不合格体験記掲示板

1. 目的
本書は、前提となる仕様書をもとに、実際のWebアプリケーションとして実装するための技術計画を定義したものです。
本サービスは、大学生向けの不合格体験記を投稿・閲覧・共感・改善点共有できる掲示板型アプリとして開発することを目的とします。

2. 開発方針
- 技術要件はシンプルかつ実装しやすい構成を採用する
- 初期開発ではMVP中心に構築し、徐々に機能を拡張する
- SQLiteを利用してローカル開発とデプロイの簡易化を図る
- フロントはHTML/CSS/JavaScript、バックエンドはPython Flaskを前提とする
- 投稿・一覧・詳細・コメント・いいね・管理機能を最優先で実装する

3. 技術スタック
3-1 フロントエンド
- HTML5
- CSS3

- BootstrapまたはCSSのみの簡易UI

3-2 バックエンド

- 画像保存時は Pillowまたは標準ファイル保存方式

3-4 開発環境

4. システム構成
- ユーザーがブラウザでアクセス
- FlaskアプリがHTTPリクエストを受ける

6. データベース設計
6-1 usersテーブル
CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    nickname TEXT NOT NULL,
    email TEXT UNIQUE NOT NULL,
    password_hash TEXT NOT NULL,
    university TEXT,
    department TEXT,
    grade TEXT,
    role TEXT DEFAULT 'user',
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

6-2 postsテーブル
CREATE TABLE posts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    title TEXT NOT NULL,
    content TEXT NOT NULL,
    category TEXT NOT NULL,
    school_year TEXT,
    department TEXT,
    failure_type TEXT,
    cause TEXT,
    reflection TEXT,
    improvement_habit TEXT,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    is_deleted INTEGER DEFAULT 0,
    FOREIGN KEY(user_id) REFERENCES users(id)
);

6-3 commentsテーブル
CREATE TABLE comments (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    post_id INTEGER NOT NULL,
    user_id INTEGER NOT NULL,
    content TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY(post_id) REFERENCES posts(id),
    FOREIGN KEY(user_id) REFERENCES users(id)
);

6-4 likesテーブル
CREATE TABLE likes (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    post_id INTEGER NOT NULL,
    user_id INTEGER NOT NULL,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(post_id, user_id),
    FOREIGN KEY(post_id) REFERENCES posts(id),
    FOREIGN KEY(user_id) REFERENCES users(id)
);

6-5 reportsテーブル
CREATE TABLE reports (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    post_id INTEGER,
    user_id INTEGER,
    reason TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    status TEXT DEFAULT 'pending'
);

6-6 tagsテーブル
CREATE TABLE tags (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT UNIQUE NOT NULL
);

6-7 post_tagsテーブル
CREATE TABLE post_tags (
    post_id INTEGER NOT NULL,
    tag_id INTEGER NOT NULL,
    PRIMARY KEY(post_id, tag_id),
    FOREIGN KEY(post_id) REFERENCES posts(id),
    FOREIGN KEY(tag_id) REFERENCES tags(id)
);

15. 合意方針に基づく改訂実装計画
この章は、機能の優先順位・認証・リアクション・感情・画像・評価に関する旧計画より優先する。実装は現行のFlask、SQLite、Jinjaテンプレートを基本とし、不要な全面構成変更は避ける。

15-1 利用ルール
- 閲覧はログイン不要とする。投稿、コメント、リアクションはログインを必要とする。
- アカウントのニックネームとは別に、投稿単位の匿名表示を可能にする。匿名表示でもDB上のuser_idは保持し、本人の編集や不正対応に利用する。
- 閲覧制限、投稿強制、1d10判定、閲覧失敗による待機は実装しない。
- 正当な利用者を妨げない範囲で、ログイン試行や短時間の連投にレート制限を設ける。

15-2 データモデル変更案
- users: 既存のnickname、email、password_hash、roleを利用する。パスワードはWerkzeugの安全なハッシュ関数で保存し、平文や単純SHA-256では保存しない。
- posts: user_idを新規投稿時に設定し、is_anonymous、mood_at_event、mood_nowを追加する。既存投稿は移行後も閲覧可能にし、所有者不明の投稿を誤って特定ユーザーへ割り当てない。
- comments: ログインユーザーのuser_idを保存し、必要に応じてコメントの匿名表示を追加する。
- reactions: post_id、user_id、reaction_type、created_atを持つ専用テーブルを設け、(post_id, user_id)を一意にする。ユーザーは1投稿につき1種類を選択し、変更時は既存行を更新する。
- 既存likesの移行では、user_idがない旧データを個人の反応と推測しない。集計を維持する必要がある場合は旧いいね数として別扱いにし、移行前にバックアップと移行方針を確定する。
- post_images: 画像ID、post_id、生成した保存キー、形式、容量、代替テキスト、作成日時を持たせる。画像バイナリはDBに格納しない。
- badges / user_badges: バッジ導入時に追加する。バッジ条件は設定可能とし、公開ランキング用の総合点は持たない。

15-3 実装フェーズ
フェーズ0：現状調査と移行準備
- DBの現行スキーマ、既存データ、テスト用DBの初期化動作を確認する。
- バックアップとロールバック手順を用意し、DB_PATHなどの設定差によるテスト干渉を解消する。
- 完了条件：本番相当データを壊さずにスキーマ移行を再実行できる。

フェーズ1：認証と投稿者紐付け
- 登録、ログイン、ログアウト、パスワードハッシュ化、セッション保護を実装する。
- 閲覧は公開のままにし、投稿・コメント・リアクションの書き込みをログイン必須にする。
- 投稿の匿名表示を追加し、作成者本人だけが自分の投稿を編集・削除できる認可を設ける。
- CSRF対策、入力検証、環境変数によるSECRET_KEY設定を行う。
- 完了条件：未ログイン閲覧ができ、未ログイン書き込み・他人の投稿編集・平文パスワード保存が拒否される。

フェーズ2：リアクション
- 既存のいいね処理を、共感・参考になった・応援したいの選択処理へ置き換える。
- DB制約で1ユーザー1投稿1リアクションを保証し、切替・取消・集計を実装する。
- 旧いいね数をどう扱うかをフェーズ0で決め、データを黙って消さない。
- 完了条件：二重登録できず、リアクション変更と取消後の件数が正確である。

フェーズ3：感情メーター
- 投稿フォームと詳細画面に任意の感情選択を追加する。
- 感情ラベルと色を対応させ、色以外のテキストまたはアイコンも表示する。
- 完了条件：未選択投稿、当時と現在の感情、キーボード操作、色以外での識別を確認できる。

フェーズ4：画像添付
- 永続性が確認できるファイルストレージを選ぶ。Render等の実行環境でローカルファイルが永続化されない場合は外部ストレージを採用する。
- 許可形式と容量上限を設定し、形式検証、安全な保存キー、削除時のファイル後始末を実装する。
- 完了条件：不正形式・上限超過を拒否し、再起動後も画像が表示され、投稿削除時に不要画像が残らない。

フェーズ5：バッジ
- ユニークな反応者数など水増ししにくい指標でバッジを付与する。
- 反応取消や不正対応を考慮し、再計算または取り消し可能な設計にする。
- 完了条件：ランキングやユーザー間の順位を表示せず、同一ユーザーの重複反応でバッジ条件を満たせない。

フェーズ6：公開前の安全確認
- 通報と管理者対応、投稿・コメントの削除、レート制限、ログ、エラー時表示を確認する。
- ユーザー入力をHTMLとして安全に出力する。現在の詳細表示でユーザー入力にsafeフィルターを使う箇所は、HTML注入を許さない表示方法へ改める。
- 本番DBの永続性、秘密情報、バックアップ、スマートフォン表示を確認する。
- 完了条件：回帰テストが通り、セキュリティと運用手順の確認項目を満たす。

15-4 テスト方針
- 各フェーズで正常系・未ログイン・権限外・重複操作・不正入力をテストする。
- DB移行は空DBと既存データ入りDBの両方で検証する。
- 画像、認証、リアクション、匿名表示、バッジを統合テストし、既存の投稿・コメントを壊していないことを確認する。
- 実装計画の各完了条件を受け入れ基準として扱い、未達のまま次フェーズへ進まない。

15-5 実装・運用設定
- 本番起動ではAPP_ENV=productionとSECRET_KEYを環境変数に設定する。本番でSECRET_KEYが未設定の場合は起動を拒否する。
- DATABASE_PATHでSQLiteファイルの場所を指定する。既存の投稿・コメント・旧いいねは起動時の冪等な列追加で保持し、旧いいねは新リアクションへ推測変換しない。
- UPLOAD_FOLDERで画像保存先を指定する。Render等の一時ファイルシステムでは再デプロイ時に画像が失われるため、永続ディスクまたは永続外部ストレージを割り当てる。render.yamlには課金を伴うディスクを自動追加していない。
- ログイン失敗は同一IPのハッシュごとに15分間で5回までとする。IPアドレスそのものはDBに保存しない。
- 管理者権限はメールアドレスだけで自動付与しない。運営者がアプリ環境で `flask --app app promote-admin メールアドレス` を実行する。
- 既存DBにパスワード未設定のアカウントがある場合は、本人確認を運営側で済ませたうえで `flask --app app set-legacy-password メールアドレス` を実行する。パスワードは対話入力し、DBにはハッシュのみ保存する。
- 画像処理にはPillowを使用する。受け入れる形式はJPEG/PNG/GIF、元ファイル上限は2MB、アップロード全体上限は5MBとする。

17. まとめ
本アプリの技術実装は、MVPを最小構成で着実に進めることで開発リスクを下げることができます。
最優先で実装すべきは、投稿・詳細・コメント・いいね・検索・基礎認証機能です。
また、大学生向けの安心感があるUIと、失敗談に対する共感を生みやすい設計を重視して実装することが重要です。

次の段階としては、
1. データベース作成SQLの完全版
2. Flaskの実装雛形
3. 各HTMLテンプレートの骨組み
4. 各機能のルーティング詳細
まで具体化して実装に進めます。
